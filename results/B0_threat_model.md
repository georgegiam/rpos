# B0 — Experimental threat model: methodology notes (issue #41, Phase 7, examiner point (ii))

Reproducible trail for the B0 deliverable. The machine-readable matrix lives in
[`B0_threat_model.csv`](B0_threat_model.csv) (regenerated by
[`../experiments/b0_threat_model.py`](../experiments/b0_threat_model.py)); this file renders the
same rows, maps each attack to the thesis threat tables, enumerates the experiment cells, and
records the honest caveats (CLAUDE.md §2 "measure, don't assert" / "flag, don't hide").

B0 is the **opening, design-only** deliverable of Phase 7 (attack experiments, examiner point
(ii) — "analysis of malicious scenarios, not just the happy path"). It contains **no measured
numbers**: it frames every later attack run (B1–B7) with the adversary dimensions the examiners
asked for and ties each attack to a row of the thesis threat tables. The measurements land in the
later B-issues.

## What B0 defines

For each of the seven attacks B1–B7, a single row fixing:

- the **adversary fraction** f it is swept over,
- whether the adversaries are **colluding or independent**,
- whether placement is **random or targeted**,
- the **metric** that will be reported (the "done when: a setting, a metric, a result graph"),
- the existing **defense** the attack probes,
- the **malicious behaviour / hook** that drives it (from
  [`../node/malicious.py`](../node/malicious.py)) and whether that code already exists,
- the **thesis Table 4.1 / 4.2 row** the attack corresponds to.

## Adversary model (the three dimensions)

- **Adversary fraction f ∈ {0, 10, 20, 30, 40, 50 %}.** f = 0 is the shared no-adversary control
  (reproduces the Phase-6 honest baseline). At the frozen emulation ceiling **N = 32**
  (`PARAMETERS.md`), f realises as an integer number of malicious containers,
  **n = round(f · 32)**:

  | f (%) | 0 | 10 | 20 | 30 | 40 | 50 |
  |---|---|---|---|---|---|---|
  | malicious nodes at N=32 | 0 | 3 | 6 | 10 | 13 | 16 |

  The seed/bootstrap node 0 is never made malicious (it is the query entry point and ring
  anchor, as in A6); malicious identities are drawn from the remaining 31.
- **Colluding vs independent.** *Independent* adversaries each misbehave in isolation; *colluding*
  adversaries coordinate (e.g. co-locate on one chunk's replica set, or jointly surround a key).
  Collusion is the stronger model and is what crosses the majority/quorum bounds.
- **Random vs targeted placement.** *Random* = malicious node IDs fall where `id = H(pk)` lands
  them (the honest distribution). *Targeted* = the adversary tries to place nodes adjacent to a
  specific chunk/key (the subject of **B2**: is node-ID grinding feasible under PoSpace admission?).

## Workload / parameters (frozen — `PARAMETERS.md`)

All B-runs use the frozen defaults: **N = 32** (emulation ceiling), **s = 3**, PoSpace challenge
timeout **δ = 2 s**, netem **5 ms / 50 ms** two-tier, per-query timeout 5 s, Zipf α = 1.0 over
1000 Tranco domains, warm-up 30 s, **seed 20260919**. Only the swept dimension (f, or the
cost/budget axis for B2/B5) varies. No frozen artifact is modified by B0 (it imports no protocol
code; the hook names are references).

## Honest caveats (flag, don't hide — CLAUDE.md §2)

1. **f at N=32 rounds to integers** (`round(f·32)` → 0, 3, 6, 10, 13, 16). The realised fraction
   is therefore slightly off the nominal % (e.g. 30% → 10/32 = 31.25%); the exact count is the
   one in the table and will be logged per run.
2. **B2 and B5 are strategy-parameterised, not f-swept.** B2's natural axis is grinding/placement
   *cost* to capture a target chunk's majority; B5's is the attacker's *storage budget* (identities
   per unit storage). Forcing them onto the f grid would misrepresent the threat; they are reported
   as cost/budget curves and the `f_values_pct` cell says so.
3. **B6 consensus eviction is deferred.** The honest eviction-after-3-fails path exists per node,
   but ring-wide consensus eviction (so one malicious challenger cannot evict an honest node) is
   Phase-7 new code; "time to eviction" depends on it.
4. **Coverage gaps are intentional and flagged.** Table 4.1's **Privacy** rows (metadata leakage,
   colluding-node linkability, traffic analysis) are outside the experimental attack scope of this
   resubmission; **Replay attacks** are mitigated by construction (TTL + hash-chained ledger) rather
   than measured; **High churn** is already answered by Phase 6 / A6; **Amortisation / Rationality**
   (Table 4.2) are Phase 1 + Phase 8 (C-series) territory. These are stated in the reverse-mapping
   tables rather than silently dropped.
5. **Thesis rows are transcribed from the external thesis** (Tables 4.1 / 4.2 are not in the repo).
   The quoted category/attack labels are the source of truth for the mapping column.

## How to reproduce

```bash
python3 experiments/b0_threat_model.py   # regenerates results/B0_threat_model.csv (deterministic)
```

No testbed, Docker, or RNG is involved — B0 is a design deliverable. A second run produces a
byte-identical CSV.

## Output schema — `B0_threat_model.csv`

One row per attack (B1–B7); columns:

- `attack_id`, `attack_name` — the B-experiment.
- `malicious_mode`, `hook` — the driving behaviour in `node/malicious.py` and the handler it
  overrides (`n/a (strategy)` for B2/B5, which are deployment strategies, not per-node behaviours).
- `f_values_pct`, `n_malicious_at_N32` — the adversary-fraction grid and its integer realisation at
  N=32 (`n/a` + an axis name for B2/B5).
- `collusion` (`independent`/`colluding`/`both`), `placement` (`random`/`targeted`/`both`).
- `metric` — what the later B-run reports.
- `defense_tested` — the existing mechanism the attack probes.
- `thesis_table` (`4.1`/`4.2`/`both`), `thesis_row` — the mapping to the thesis threat tables.
- `code_status` — `behaviour plumbed` / `needs driver` / `needs new code`, so the table doubles as
  the Phase-7 work ledger.
- `note` — a one-line clarification.
